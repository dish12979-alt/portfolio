盾构隧道数字孪生与 AI 诊断系统

Product Thinking

复杂工程场景的产品化挑战

这个项目的核心不是把数据“画出来”，而是把分散的工程对象、时间过程和诊断依据组织成可理解、可复盘、可解释的产品体验。

用户与场景

  • 课题组研究人员需要展示研究成果与系统能力
  • 合作单位相关人员需要快速理解施工状态和风险解释
  • 未来工程管理人员需要复盘施工过程并定位异常状态

关键痛点

  • 工程数据来源分散，CSV、传感器、GeoJSON、GLB、钻孔数据难以统一理解
  • 线路、盾构、地层、管片、监测点之间缺少统一空间视图
  • 盾构推进参数是时序过程，静态表格难以支撑复盘分析
  • AI 诊断如果只给结论，用户难以判断依据是否可信

产品方案

三维主场景统一展示线路、站点、盾构、监测点和地层对象
时序播放器支持按施工时间复盘推进过程
地层建模模块将钻孔和地层数据转化为空间对象
AI 诊断侧栏展示风险等级、关键指标和解释依据

Prototype Modules

核心功能模块展示

原型围绕“看清空间关系、回放施工过程、解释诊断依据”组织核心模块，展示复杂工程数据如何被转化为可浏览、可复盘、可解释的产品体验。

三维主场景

统一展示地铁线路、站点、监测点与地下空间对象，作为整个数字孪生原型的空间底座。

盾构监控与 AI 诊断

把施工趋势、结构指标、风险等级和诊断解释放在同一视图中，避免 AI 只输出单句结论。

掘进模拟

用三维动画表达盾构推进、管片拼装和施工参数变化，服务演示汇报场景。

时序回放与趋势分析

围绕推进速度、总推力、刀盘响应等指标，支撑施工过程复盘。

地层与钻孔建模

将钻孔、地层面和开挖区域转化为空间对象，辅助理解施工环境。

环片监测视图

展示监测区段、环片状态和关键变形指标，用于结构安全状态解释。

AI Coding Observation

AI Coding 在复杂项目中的使用体验观察

该项目开发过程中，我深度使用 Claude Code / Codex 辅助需求拆解、组件开发、后端接口、数据处理和调试。 我的观察来自真实复杂代码库，而不是简单 demo。

我的使用流程

  1. 需求拆解将系统拆分为三维场景、数据回放、地层模块、AI 诊断侧栏等任务
  2. 上下文组织提供项目结构、关键文件、字段含义和业务规则
  3. 代码生成辅助开发 Vue 组件、FastAPI 接口、Python 数据脚本
  4. 调试修复根据报错、页面表现和接口返回结果多轮修正
  5. 人工验收检查字段、链路、交互和业务逻辑是否符合预期

真实痛点

上下文容易断裂

多文件任务中，AI 容易只改当前文件，漏掉 API、composable、组件和字段之间的联动。

领域字段理解不稳定

盾构环号、推进段、A-F 分区推力、结构利用率等字段有工程含义，需要反复补充背景。

缺少任务级验收闭环

AI 能生成代码，但很少主动说明改了哪些文件、影响哪些页面、应该验证哪些交互。

压缩后信息缺失

为了适配上下文长度，压缩项目说明后容易丢失关键约束，导致后续生成结果偏离真实业务逻辑。

如果我是 AI Coding 产品 PM

  • 代码库上下文地图：帮助 AI 理解主链路和依赖关系
  • 任务级开发计划：修改前说明影响范围和风险点
  • 验收面板：生成 diff 摘要、验证清单和潜在问题提示

这个项目让我理解到：AI Coding 的核心价值不只是生成代码，而是在复杂业务项目中帮助开发者稳定理解上下文、控制变更风险，并完成可验证的任务闭环。
